minilake on :8000 — Databricks REST emulator on DuckDB: Unity Catalog registry, Files API, SQL warehouse lakehouse-wh, web SQL editor
pipeline/lake.py drives every arrow above: setup → land → bronze → silver → gold → redshift → verify. It talks to minilake over REST (httpx), transforms with DuckDB, writes Delta with delta-rs, and loads Postgres through DuckDB's postgres extension.

Why Delta on a local folder?

The s3/ tree is laid out exactly like the bucket (<bucket>/<layer>/<table>/), so each s3:// URI maps 1:1 to a path. Each table is real Delta: Parquet files plus a _delta_log/, readable by any Delta engine.

Why register in minilake?

minilake gives the tables Databricks-shaped identities (lakehouse.gold.daily_sales) and serves them over the same REST and SQL APIs as Databricks, so the SDK, the SQL editor and REST clients work unchanged.

Why Postgres for Redshift?

Redshift speaks the PostgreSQL wire protocol, so clients, drivers and the load pattern (staging table + swap + audit row) behave the same. Redshift-only DDL (DISTKEY, SORTKEY, SUPER, Spectrum) is not available locally.
