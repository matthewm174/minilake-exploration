Anatomy of one table registration

_register() → POST /api/2.1/unity-catalog/tables 
{
  "name": "orders", "catalog_name": "lakehouse", "schema_name": "bronze",
  "table_type": "EXTERNAL", "data_source_format": "DELTA",
  "storage_location": "D:/git/minilake/s3/acme-lakehouse/bronze/orders",
  "comment": "Raw order events (JSON lines, nested items …)",  ← line 1 of the .sql
  "properties": {
    "emulated_s3_uri": "s3://acme-lakehouse/bronze/orders",
    "medallion_layer": "bronze",
    "source_sql": "sql/bronze/orders.sql" }
}

Why the local path, not s3://?

minilake rejects s3:// storage locations, so storage_location is the local folder and the S3 URI it stands for is kept in the emulated_s3_uri property. The mapping is mechanical: s3://X ⇄ ./s3/X (s3_to_local()).

No column list is sent. UC reads the schema from the Delta log, so rewriting a table never needs re-registration — unless its location or comment changes, in which case the entry is deleted and re-created.

Idempotent by design

ensure_catalog / ensure_schema / ensure_volume only POST after a 404, and the warehouse is looked up by name before creating.

setup also scans s3/acme-lakehouse/*/* and re-registers every folder that has a _delta_log, which rebuilds the catalog after a minilake crash.

reset deletes the catalog with force=true and removes s3/.
