Redshift load — step_redshift()

Every gold table is copied into Postgres (the Redshift stand-in) with the same pattern production uses: load a staging table, then swap it in with one transaction and write an audit row. A query against analytics.daily_sales sees either the old table or the new one — never an empty or half-loaded table.

Production equivalent (Redshift SQL)

CREATE TABLE analytics.stg_daily_sales (LIKE analytics.daily_sales);
COPY analytics.stg_daily_sales
  FROM 's3://acme-lakehouse/gold/daily_sales/'  -- or a manifest
  IAM_ROLE 'arn:aws:iam::<acct>:role/redshift-copy'
  FORMAT AS PARQUET;
BEGIN;
  DROP TABLE analytics.daily_sales;
  ALTER TABLE analytics.stg_daily_sales RENAME TO daily_sales;
COMMIT;
Run by Airflow, Step Functions or a Databricks job after gold finishes.

Versions and counts match the current gold tables; loaded_at defaults to now(). Query: SELECT * FROM analytics.load_audit ORDER BY loaded_at DESC

Local vs. real Redshift

  • Same wire protocol, db dev, user awsuser, port 5439 — clients and drivers work unchanged.
  • No DISTKEY, SORTKEY, SUPER, UNLOAD, Spectrum or COPY FROM 's3://': keep that DDL in deployment code.
  • Cross-check: channel totals from lake.py verify (via minilake) must equal SELECT channel, sum(revenue) FROM analytics.daily_sales GROUP BY 1.
  • New sql/gold/x.sql ⇒ new analytics.x, no loader change.
