Inside a layer step — step_layer(ml, layer) and the Delta tables it writes

The same function builds bronze, silver and gold. Adding a table means adding one SQL file: the file name is the table name. DuckDB does the transform; delta-rs writes the result as a new Delta version; minilake records where it lives.

1 · _engine(ml)

Build a DuckDB session that sees the catalog

con = duckdb.connect();  SET TimeZone = 'UTC';  LOAD delta
ATTACH ':memory:' AS lakehouse
for schema in bronze, silver, gold:
    for t in GET /unity-catalog/tables?schema_name=schema:
        CREATE VIEW lakehouse.<schema>.<t> AS
            SELECT * FROM delta_scan('<t.storage_location>')
So FROM lakehouse.silver.orders in any SQL file resolves to the current Delta version of that folder — the same three-part name Databricks would use.

A reader replays the log to find the live file set. delta_scan(), minilake and the Redshift loader all do this, so they never see the tombstoned file.

Why not just write Parquet?

Overwrite is atomic: readers see either v0 or v1, never a half-written folder. Every version is addressable (DeltaTable(loc).version() is what load_audit records), and the schema lives in the log so UC needs no column list.

Why the Redshift COPY caveat?

The folder holds files from old versions too. A naive COPY … FROM 's3://…/silver/orders/' would load 299 + 598 rows. Production uses a manifest (GENERATE symlink_format_manifest) or Spectrum; locally delta_scan avoids it.

Ordering rule

Files in a layer run alphabetically, and each layer only sees tables registered before it starts plus files already run in this layer. A file may read from earlier layers, or from an earlier file in the same layer (e.g. a gold b_*.sql could read lakehouse.gold.a_*).
